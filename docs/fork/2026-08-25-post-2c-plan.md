## The rename, and why it is not happening

The 2d rename was planned, scoped (266 files, 4159 occurrences, 9 crates and
their directories, a config/session migration shim) and then dropped after the
trade was laid out. It delivered no functional value, and it carried the only
runtime failure surface left in the project - config dir, socket path, PATH-shim
basenames, the ai-hook sibling lookup, MCP re-registration - none of which the
1725 tests or the census can see. The two arguments that made it urgent had both
weakened by then: the repo is private, and self-update is disabled, so there is
no public distribution where the product name is doing any work.

What genuinely had to change was **upstream's identity**, not the product name:
`CFBundleIdentifier = io.github.arthurdev44.paneflow`, `authors = ["Arthur"]`,
and the `repository`/`homepage` pointing at upstream. macOS keys TCC grants,
LaunchServices and the preferences domain off the bundle id, so signing under
your own Apple Team ID while claiming someone else's reverse-DNS is wrong and
collides with an installed upstream build. That is task 12 - four files.

GPL-3.0-or-later attribution to upstream is satisfied by `LICENSE` and the
README line, not by the bundle id. Both stay.

If PaneFlow is ever distributed publicly under its own identity, revisit the
rename then, against a tree that is by that point much smaller.

Task 15 swept leftover PanesCLI product-name prose and `theaamgroup/panescli`
repo URLs. Mentions of PanesCLI remaining in this file are the
considered-and-dropped record: the rename was scoped and is not happening.

## Operating rules for an unattended run

Decided 2026-08-25 alongside the plan:

- **Branch.** Work on `main`. Push **after each task's integrated, gate-verified
  commit** - work is never stranded locally, and once task 2 lands each push
  exercises CI.
- **When a task turns out bigger or riskier than its description:** finish the
  unambiguous part, write up precisely what could not be resolved and why,
  create a follow-up task, and move on. Do not halt the whole run on one
  ambiguity, and do not proceed on an assumption that lands in the tree. This is
  how stage 2c handled its 15 deferred config-schema items.
- **Anything a build cannot prove goes in `MANUAL-CHECKLIST.md`** (task 16), with
  exact steps and a falsifiable expected result - not "workspaces work" but "the
  second workspace becomes active". Never tick an item on the user's behalf.
  But the bar is "can a machine actually establish this", not "is it tedious":
  **the visual smoke test is automatable** - launch the app, screenshot it, and
  look. The font-kit failure mode (every glyph an empty box) is visible in a
  screenshot and passes every other gate, so that check is the agent's job and
  should be the FIRST act of the run, before any task, to establish that HEAD
  works. Otherwise fourteen tasks land on a possibly-broken tree and the review
  at the end cannot attribute breakage. Cmd+Tab genuinely cannot be automated -
  it is the chord macOS intercepts.
- **Still ask before:** tagging, creating any secret, or anything outward-facing
  beyond the per-task push.

The manual checklist matters more than it looks. Stage 2c deleted ~9,500 lines
verified by compile, tests and census alone. The `font-kit` regression CLAUDE.md
warns about - every glyph rendering as an empty box - passes all three.

## The execution model that worked, and should be reused

Stage 2c ran twelve delegated batches with zero re-briefs. The thing that made
it work is worth stating plainly, because the old advice in STATE.md said the
opposite and was wrong:

> **Fan-out works when the worker does not have to discover anything.**

The briefs stopped saying "find the Linux code" and started carrying the exact
site list - `file:line`, the cfg expression as written, the action, the
reduction. That list came from a read-only inventory phase that ran *before* any
edit. A batch that must find its own targets in a codebase this interleaved will
eventually delete a `cfg(unix)` arm.

### Mechanics

```bash
GROK="$HOME/.grok/bin/grok"            # never bare `grok` - that is the PATH shim
git worktree add /Users/dayers/Github/pf-X -b <branch> mac-only-fork
cp -c -R target /Users/dayers/Github/pf-X/target   # APFS clone: ~27s for three, ~0 bytes
"$GROK" --prompt-file brief-X.md --cwd /Users/dayers/Github/pf-X \
        --max-turns 100 --json-schema "$(cat schema-exec.json)" \
        > out-X.json 2>err-X.txt
```

- Worktrees are reusable between waves: `git -C <wt> reset --hard` then
  `git -C <wt> checkout -B <branch> mac-only-fork`.
- Three concurrent batches was the working cap on this machine.
- **Disjoint file sets are what make concurrency safe.** Two batches editing the
  same file collide at `git apply` time even when their edits are six lines
  apart. Check the allowlists against each other before launching.
- Agents never touch git. They leave edits unstaged; the orchestrator collects
  `git -C <wt> diff`, applies it to the main worktree, re-runs all five gates
  **itself**, and writes the commit.

### Every brief opens with this, verbatim

> `#[cfg(unix)]` is TRUE on macOS. macOS IS a unix. Never remove one.
> `unix` is not `linux`. Only `all(unix, not(target_os = "macos"))` is Linux.

152 `cfg(unix)` and 77 `cfg(macos)` sites survive deliberately. That warning is
why no batch in 2c got it wrong.

### Every brief carries this gate contract

```bash
cargo fmt                                # FIRST, not last
cargo build                              # exit 0
cargo clippy --workspace --all-targets   # exit 0 AND warning count exactly 1
cargo test --workspace                   # compare NAMES, never the count
cargo fmt --check                        # exit 0
./scripts/linux-census.sh                # report the totals AND the negative control
```

`cargo fmt` runs first because rustfmt collapses a surviving block onto one line
and makes `unused_braces` fire only on the reformatted source. **Clippy exits 0
with warnings**, so "clippy exit 0" is not evidence - the warning COUNT is.
There is exactly one pre-existing warning (`block v0.1.6`) and it is not ours.

### Integration protocol

1. Read the agent's structured result. Check `num_turns` - a `1` on an
   open-ended task means `--json-schema` suppressed the tool loop and the answer
   is fabricated. (It is legitimate when the whole task is inline in the prompt,
   as with the blind verifier.)
2. Read the actual diff. Agent "green" claims are never the evidence; in stage
   2b a batch reported green from a clippy run that predated its own final edits.
3. `git apply --check` then `git apply` into the main worktree.
4. Run all five gates yourself, plus the census.
5. **Diff the sorted test-name list against the previous commit's.** Every
   removal and every rename gets named in the commit message with the
   arithmetic. This is how 65 removals and 4 renames stayed auditable.
6. `cargo fmt --check` immediately before `git commit` - the release pipeline
   runs it inside every build leg, and a tag push on a dirty commit burns a
   ~25 min run and cannot be salvaged without re-tagging.

### CI findings, and which blockers are real

Task 17 read the actions/runner-images manifests rather than reasoning about
what runners probably ship. Three results:

- **`runs-on: macos-13` is scheduling against a retired image.** The published
  set is now macos-14, macos-15 and macos-26 (each with an `-arm64` variant).
  `release.yml`'s Intel leg cannot be scheduled at all. That is the *second*
  independently fatal thing in that pipeline, after the `libghostty-windows`
  feature that does not exist.
- **Xcode:** macos-15-arm64 defaults to Xcode 16.4 (with 26.x also installed);
  macos-26-arm64 defaults to 26.6 and carries no 16.x line.
- **The manifests do not settle the Metal question** - neither mentions "metal"
  or "downloadComponent". Since Xcode 26 ships the Metal toolchain as a separate
  component, the workflow must PROVE it at runtime with `xcrun metal --version`
  (never `xcrun -f metal`, which succeeds on a machine that cannot build) and
  run `xcodebuild -downloadComponent MetalToolchain` if that fails. Written that
  way it survives an image bump instead of breaking silently.

Two dependency edges turned out to be **advisory, not real**. The task tool
cannot express a soft edge, so they are recorded here:

- **4 -> 2 is soft.** `run_tests.yml:402` re-implements the size budget in YAML
  against a hardcoded ELF path, but `src-app/build.rs` already enforces
  `EMBED_SIZE_LIMIT_BYTES` itself on every build
  (`enforce_embed_size_budget`, build.rs:159). Task 2 should DELETE the
  redundant YAML step and let build.rs fail the build. Task 4 is then needed to
  make that cap honest on Mach-O, but task 2 does not wait for it.
- **12 -> 3 is not real at all.** `release.yml:300` names
  `assets/io.github.arthurdev44.paneflow.metainfo.xml`, which is why the edge
  was drawn - but that file **no longer exists**. It is AppStream metadata for
  `.deb`/`.rpm` (GNOME Software / KDE Discover) and was deleted with the Linux
  packaging in stage 1. So the "Validate AppStream metainfo" step is already
  broken, and task 3 deletes it rather than renaming anything.
- **13 -> 3 is soft.** Task 3 strips `POSTHOG_API_KEY` (release.yml:533, :569)
  whether or not telemetry has been removed yet - the decision is locked either
  way. Doing 13 first just makes it mechanical.

Net: after task 17, **only task 14 is genuinely blocked**, and that one is
deliberate - a version bump invalidates every doc that quotes 0.8.2.

Tasks 2 and 3 were deleted and recreated as **18** and **19** without those
stale edges, because `TaskUpdate` can add a blocker but not remove one and a
list that misreports its own readiness will idle an unattended run. Neither workflow currently installs the Metal toolchain; both only check
`xcode-select -p` for Command Line Tools, which CLAUDE.md is explicit is NOT
sufficient - GPUI compiles Metal shaders at build time. If the GitHub runner
image lacks the toolchain, the workflows are being written against a runner that
cannot build the app, and it surfaces only on the first CI run. Read the
runner-image manifest; do not reason about what runners probably ship. And never
check with `xcrun -f metal`, which reports success on a machine that cannot
build.

Full detail - exact sites, traps, per-task verification - lives in the task
descriptions, not here.

## Method rules that apply to all of it

From `docs/fork/STATE.md`, repeated because they are the ones most likely to be
skipped under time pressure:

1. **Never report a finding you have not observed.** Four claims in this project
   have been falsified by executing something. Task 6 exists entirely because a
   keybinding claim needs observing rather than reasoning about.
2. **Add a control.** If the control reproduces the positive result, the
   experiment is broken. The blind `cfg!()` verifier in 2c carried a planted
   CHANGED hunk for exactly this reason, and it caught an over-claim of mine.
3. **Do not pipe a command whose exit code matters.** `cargo test | tail`
   reports `tail`'s status. Redirect as `cmd > file 2>&1`, never
   `cmd 2>&1 > file`.
4. **A green `cargo build` is not a green tree.**
5. **A detector only measures the shape it was written for.** The census
   measures cfg predicates. Ungated code, enum variants, `Cargo.toml` tables,
   embedded assets, workflow files and user-facing strings each need their own
   sweep.
6. **Inventory line numbers go stale the moment you commit.** Re-derive
   `file:line` from the live tree before writing a brief, and tell the agent to
   stop and report if a line does not say what the brief claims.
